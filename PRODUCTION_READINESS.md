# AegisRun Production Readiness Assessment

**Assessment date:** 2026-09-25  
**Application release assessed:** v1.0.1  
**Evidence bundle format:** 1.0.0  
**Status:** **Production-ready core; package-registry distribution incomplete**

## Executive summary

AegisRun's core repository, security gates, container release path, verifier artifacts, and GitHub release process have reached a production-oriented baseline. The September 2026 hardening cycle closed the security, dependency, deployment, migration, client-IP trust, release-integrity, and npm production-dependency issues that were still open in the February assessment.

The remaining release gap is distribution-specific: the v1.0.1 Python and TypeScript SDK jobs successfully built and generated provenance attestations, but publication to PyPI and npm failed because registry credentials/trusted publishing were not configured. This does not invalidate the source release, verifier binaries, SBOMs, or container artifacts, but it means `pip install aegisrun==1.0.1` and `npm install @aegisrun/sdk@1.0.1` are not yet supported from the public registries.

## Current release evidence

### Repository and normal CI

On the v1.0.1 release line:

- normal CI is green;
- standalone Security Scan is green and operational;
- release-branch Release Gate completed successfully;
- dependency lockfiles were generated by npm rather than hand-edited;
- high/critical production npm findings are fail-closed;
- Go vulnerability checks cover both API and verifier modules;
- workflow linting is part of normal CI.

### v1.0.1 release workflow

The v1.0.1 release run completed these stages successfully:

- Release Preflight;
- Release SBOM;
- Release Security Gate;
- Build and Push Images;
- build-provenance attestations.

The registry publication stages failed only at authentication:

- Python SDK: PyPI upload returned HTTP 403 because `PYPI_API_TOKEN`/trusted publishing was not configured;
- TypeScript SDK: npm returned `ENEEDAUTH` because `NPM_TOKEN`/trusted publishing was not configured.

Because the original workflow required both package-publish jobs before `create-release`, its GitHub Release job was skipped. A recovery workflow then successfully created the public **AegisRun v1.0.1** GitHub Release with verifier binaries, checksums, and four SPDX SBOM files.

## Remaining gaps

### 1. PyPI trusted publishing

**State:** open.

Configure PyPI Trusted Publishing/OIDC for the `aegisrun` project and update the release workflow to publish without a long-lived API token.

**Exit criterion:** a release or dedicated recovery job publishes the intended Python package successfully and verifies it from PyPI.

### 2. npm publishing authentication

**State:** open.

Configure npm trusted publishing/OIDC where supported for the package/workflow, or provision the minimum required publish credential.

**Exit criterion:** the TypeScript SDK publishes successfully and can be installed from the npm registry.

### 3. Release-stage fault isolation

**State:** open hardening improvement.

The v1.0.1 run demonstrated that registry publication failure can prevent the normal GitHub Release job even after images, SBOMs and attestations are complete.

**Target:** decouple GitHub Release creation from optional registry publication so each distribution channel reports its own status without hiding successful artifacts.

### 4. Environment-specific operations evidence

The repository contains the alerting/on-call structure, but each real staging/production deployment must supply and test its own receiver endpoints, secrets, OIDC provider, database TLS configuration and backup destination.

This is deployment evidence, not something that can be proven by repository contents alone.

## Production deployment conditions

Before declaring a specific environment live:

1. Configure real OIDC; mock OIDC must not be used.
2. Configure non-default database credentials and TLS.
3. Configure explicit CORS.
4. Configure client-IP trust correctly for the deployment topology.
5. Configure and test backups/restores.
6. Configure on-call receiver endpoints.
7. Run release gates and environment smoke tests.
8. Record image digests, migration version and rollback target.
9. Complete the release checklist and attach evidence.
