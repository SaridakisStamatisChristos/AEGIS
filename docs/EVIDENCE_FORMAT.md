# AegisRun Evidence Bundle Format

**Bundle format version:** 1.0.0  
**Compatible application baseline:** AegisRun v1.0.1  
**Reviewed against implementation:** 2026-09-25

The evidence bundle format version is independent from the AegisRun application version.

## 1. Purpose

An evidence bundle is a ZIP archive containing the persisted run record, append-only event chain, policy snapshot and signature metadata required for offline verification.

It is designed for audit, incident review, chain-of-custody analysis and independent integrity verification.

## 2. Current archive layout

The implementation in `api/internal/ledger/bundler.go` writes:

```text
bundle.zip
├── manifest.json
├── events.jsonl
├── policy_snapshot.json
├── run.json
├── public_key.pem        # present when the signing key can be loaded
└── README.txt
```

The current format does **not** use a separate `signature.json`, `blobs/` directory or `merkle_proof.json`.

## 3. manifest.json

The manifest fields are:

```json
{
  "bundle_version": "1.0.0",
  "run_id": "01RUN",
  "exported_at": "2026-09-25T06:00:00Z",
  "event_count": 42,
  "root_hash": "<run evidence hash>",
  "signature": "<base64 signature>",
  "signer_key_id": "<key id>"
}
```

Semantics:

- `bundle_version` — evidence archive contract version;
- `run_id` — run represented by the bundle;
- `exported_at` — export timestamp in UTC;
- `event_count` — number of exported events;
- `root_hash` — run evidence/root hash persisted at completion;
- `signature` — run evidence signature;
- `signer_key_id` — signing-key identifier.

## 4. events.jsonl

Contains one JSON-encoded event per line in sequence order.

An event includes:

- `event_id`;
- `run_id`;
- `seq_no`;
- `event_type`;
- `timestamp`;
- `payload`;
- `prev_hash`;
- `event_hash`.

The event chain is tamper-evident: each event hash commits to the event's canonical content and previous hash according to the ledger implementation.

## 5. policy_snapshot.json

Contains the exact policy version associated with the run, including its specification and `spec_hash`.

The offline verifier uses the snapshot to check that the policy content matches the hash referenced by the evidence.

## 6. run.json

Contains the persisted run record, including:

- policy reference;
- state-schema reference when present;
- metadata;
- status/outcome;
- counters;
- evidence hash;
- signature;
- signer key ID.

## 7. public_key.pem

When the signing key can be loaded, the bundle contains the Ed25519 public key in PEM form.

Private key material is never exported in the bundle.

## 8. README.txt

A human-readable summary generated by the bundler. It identifies the run and describes the archive contents and verifier command.

## 9. Verification

Use a release verifier binary:

```bash
aegis-verify bundle.zip
```

The verifier checks the bundle structure and performs, at minimum:

1. event-chain integrity verification;
2. policy snapshot integrity checks;
3. Ed25519 signature verification using the bundled public key/signature metadata.

The verifier returns a non-success result when required integrity/signature checks fail.

## 10. Server-side verification

`POST /api/v1/evidence/verify` is not the same as full offline bundle verification. It verifies the stored event chain for a requested run.

For independent evidence validation, export the ZIP and use `aegis-verify`.

## 11. Hashing and signing source of truth

Normative implementation paths:

- `api/internal/ledger/hasher.go`
- `api/internal/ledger/signer.go`
- `api/internal/ledger/bundler.go`
- `verifier/internal/`
- `api/internal/contracts/types.go`

Do not infer a Merkle-tree/blob format from older design text; the files above define the v1.0.0 bundle currently emitted.

## 12. Compatibility

AegisRun application v1.0.1 emits bundle format 1.0.0. An application patch release does not require a bundle-format bump unless the serialized evidence contract itself changes incompatibly.

Historical bundles should remain immutable. New readers should preserve compatibility with stored evidence according to the project's schema-version policy.
